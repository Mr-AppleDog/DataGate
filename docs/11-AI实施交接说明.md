# 11 AI 实施交接说明

## 1. 给实施 AI 的任务

你要实现的是一套面向公司内部全员、集中托管数据库凭据、按资源授权、受控执行并完整审计的生产级数据库访问治理平台。它对标阿里云 DMS + DAS 的核心内部治理能力，但采用开源自建方式，不能只做一个把 SQL 转发给 JDBC 的页面。

项目基于 RuoYi-Vue-Plus 5.X，精确基线为：

- 后端 dromara/RuoYi-Vue-Plus v5.6.2，commit 8136a01；
- 前端 CrazyLionCat/plus-ui v5.6.2-v2.6.2，commit d0d4519；
- Java 17；
- Spring Boot 3.5.15。

如果实际依赖清单与本文档出现差异，以精确 tag 内的构建文件为准，并在变更记录说明；不得私自切换 main/master、旧版 4.X、Single 精简版或另一套管理框架。

## 3. 开始前的仓库检查

1. 阅读仓库根目录以及相关子目录的 AGENTS.md 或同等约束；
2. 检查 git status，保留用户已有改动，不覆盖不相关文件；
3. 确认当前 tag/commit 和前后端版本；
4. 阅读上游 README、LICENSE、pom.xml、前端 package.json 和模块结构；
5. 运行原始构建和测试，保存基线结果；
6. 搜索默认密码、演示接口、注册入口、P6Spy、Swagger 暴露和多租户配置；
7. 建立需求 ID → 模块 → API → 数据表 → 测试的追踪表；
8. 核验 v5.6.2 工作流任务改派及相邻端点的对象级授权，公开 Issue #44 不能因处于关闭状态而跳过；
9. 先输出实施计划和风险，再进入 M0。

严禁安装或使用 Anaconda 相关软件。需要 Python 辅助时只能使用项目允许的普通 Python 环境，并且不得让 Python 取代简单、可审计的构建或迁移流程。

## 4. 不可更改的产品决定

- 公司内部单组织，不做面向外部客户的 SaaS；
- 首期本地账号，无公开注册；LDAP/OIDC/钉钉只留 SPI；
- 1,000 用户、300 数据源、100 在线、50 并发查询；
- P0 同时支持 MySQL、PostgreSQL、Redis/Tair；
- 生产普通用户只读和安全 EXPLAIN；
- 导出、DML、DDL、Redis 写入分别授权并审批；
- 查询、变更、监控账号分离；
- 凭据采用 AES-256-GCM 信封加密，KEK 在数据库之外；
- 查询审计 1 年，授权/导出/DDL/DML 审计 3 年；
- 慢查询每分钟采集，目标 5 分钟内告警；
- P0 通知为钉钉、邮件、通用 Webhook；
- 生产至少 2 应用节点，RPO 15 分钟、RTO 1 小时；
- 内网/VPN 使用，目标数据库只放行平台执行网络。
- 平台内部会话、缓存和锁默认使用 Valkey；如改用 Redis，先锁定版本并完成许可证合规确认。

这些是用户已确认的需求，不应再次向用户提问。

## 5. 必须保持的技术边界

### 5.1 RuoYi 负责的部分

- 用户、部门、岗位、角色、菜单；
- Sa-Token 登录与会话基础；
- MyBatis-Plus、Redisson；
- WarmFlow 审批编排；
- SnailJob 调度和重试；
- 通用 CRUD、字典、参数、操作日志和管理界面。

### 5.2 新平台必须独立实现的部分

- 外部数据源资源树和资源授权；
- Allow/Deny、继承、条件、有效期和授权版本；
- 凭据保险箱；
- SQL/Redis 解析、授权、受控执行、取消；P0 SQL AST 使用 Alibaba Druid Parser，目标连接池使用 HikariCP；
- 查询、导出、变更的专用审计；
- 慢查询统一模型、采集、指纹、聚合和治理；
- 通知通道 SPI；
- 审计哈希链、归档和验证。

禁止以下替代：

- 用 RuoYi 数据权限替代目标数据库资源授权；
- 用 dynamic-datasource 直接承载用户 SQL；
- 用 P6Spy 或框架操作日志替代查询审计；
- 用前端按钮隐藏替代服务端鉴权；
- 用正则或关键字搜索替代方言 AST；
- 用前端脱敏替代服务端流式脱敏；
- 用共享数据库账号的数据库日志替代平台个人审计。

## 8. 编码规则

- 领域模型不直接依赖控制器 DTO；
- 连接器只能通过定义好的 SPI 被业务层调用；
- 禁止在控制器拼 SQL 或操作 JDBC；
- 所有状态迁移经领域服务，Repository 不允许任意状态 UPDATE；
- 时间统一以 Instant/UTC 存储；
- 主键、版本号、幂等键和审计 eventId 语义明确；
- 数据库唯一约束作为并发正确性的最后防线；
- 异常对外转换为 05 文档稳定错误码；
- 日志只记录 ID、fingerprint、耗时和错误码；
- Secret 使用专用类型，toString 永不返回值；
- 敏感 DTO 不允许 Lombok 自动生成包含所有字段的 toString；
- SQL/命令参数不能通过字符串拼接传给驱动；
- 所有连接、Statement、ResultSet 在异常和取消路径可关闭；
- 变更操作默认要求幂等键和乐观锁。

## 9. 数据库实现要求

- 以 04 文档为逻辑模型，迁移文件为最终物理事实；
- 先创建外键依赖少的基础表；
- 热点事件表按时间分区；
- JSONB 仅用于扩展属性，不隐藏核心查询字段；
- 唯一约束覆盖幂等和活动授权冲突；
- 软删除不适用于不可变审计事件；
- 密文字段和原 SQL 加密字段采用 bytea/二进制语义；
- 索引需由真实查询和 EXPLAIN 验证；
- 测试同时覆盖迁移前进、全新安装和版本升级；
- 生产迁移不允许修改已发布 migration。

## 10. 前端实现要求

- 复用 plus-ui 的布局和权限指令，但所有权限仍由后端复核；
- 查询控制台需清楚显示环境颜色、数据源、库/模式、只读状态和限制；
- 生产执行前明确环境，不用容易误点的默认选择；
- 危险或审批动作展示原因、资源、有效期和影响；
- 凭据表单提交后不回填；
- SQL、错误和数据单元格按文本渲染，防 XSS；
- 导出按钮与普通查询按钮分离；
- Redis 使用结构化命令表单或可靠 tokenizer，不能简单按空格拆分；
- 大结果使用虚拟滚动但不绕过服务端上限；
- 所有异步状态可通过 executionId/jobId 恢复，不依赖当前页面内存。

## 11. 测试要求

### 11.1 真实引擎

CI/集成环境至少启动受支持版本的 MySQL、PostgreSQL 和 Redis 测试实例。账号分为查询、变更、监控并按最小权限创建。测试要验证目标库实际状态，而不是只断言平台返回“拒绝”。

### 11.2 安全语料

把 06 和 08 文档中的语料做成版本化数据集。每次解析器、驱动、连接器升级都运行全部回归，并断言：

- 拒绝请求未发送到目标库，或目标库零副作用；
- 引用资源集合完整；
- 未知语法失败关闭；
- 审计存在且不含敏感字面量。

### 11.3 性能

逐级执行 10、25、50 并发查询；覆盖窄结果、宽结果、超限、慢客户端、取消。慢查询管道做至少每日百万事件等效的持续压测。

### 11.4 恢复

不能用“备份成功日志”代替恢复验证。必须在隔离环境恢复 PostgreSQL、KEK 和审计归档，并记录实际 RPO/RTO。

## 12. 禁止的捷径

- 把明文密码放在 application.yml、环境模板或数据库；
- 提供查看/复制数据源密码的管理员接口；
- SQL 解析失败后交给数据库试运行；
- 先执行再根据异常判断是否有权限；
- 默认授予 DBA 所有业务数据读取权；
- 把查询结果存到审计、日志或 Redis；
- 让导出复用 SELECT 权限；
- 审批后允许直接编辑 SQL；
- 用一个数据库账号同时查询、变更、采集；
- Redis 开放 KEYS、EVAL、MONITOR、CONFIG 等危险命令；
- PostgreSQL 默认开放 EXPLAIN ANALYZE；
- 把动态数据源组件当用户查询网关；
- 生产单节点、无备份或未演练就宣布可上线；
- 未经用户授权接触真实生产凭据或执行生产变更。

## 13. 如何处理文档未覆盖的问题

可以自行决定低风险实现细节，但必须满足：

1. 不改变已确认的产品范围和安全属性；
2. 优先失败关闭、最小权限和可审计；
3. 在 ADR 或 assumptions.md 记录选择、替代方案和影响；
4. 可逆且不扩大外部影响；
5. 不凭空声称已验证。

遇到以下情况必须停下询问用户或负责人：

- 需要访问真实生产系统、凭据或公司网络；
- 要改变已确认的支持引擎、审批链或保留期；
- 要弱化加密、审计、只读、TOTP、双人审批或灾备目标；
- 需要购买商业服务或使用有许可证风险的组件；
- 发现上游版本与精确 tag 不存在或存在重大不兼容；
- 需要破坏性修改用户已有代码/数据。

## 14. 每次交付报告格式

报告应简洁且可复核：

- 完成的需求 ID 和里程碑；
- 新增/修改文件；
- 数据库迁移版本；
- 执行的构建、测试和结果；
- 安全/性能/恢复证据；
- 与规格的偏差和 ADR；
- 尚未完成的项目与风险；

不要只说“已完成”或“理论可用”。所有完成声明都应指向可运行代码、测试输出或可检查配置。

## 15. 最终完成定义

只有在以下事实同时成立时，实施 AI 才能向用户报告“真实可上线”：

- 10 文档的 12 个产品级最终验收场景全部通过；
- 三种引擎的安全和集成测试通过；
- 100 在线、50 并发、300 数据源、百万慢事件容量验证通过；
- 生产高可用部署和监控告警可用；
- 实测 RPO ≤ 15 分钟、RTO ≤ 1 小时；
- 凭据、SQL、结果和审计的安全测试通过；
- 无阻断级漏洞和未处置高危依赖；
- DBA、安全、运维和业务负责人完成上线签字；
- 已从低敏单数据源完成灰度且观察期无 P1 事故。

在此之前，应准确报告“已完成某里程碑/可进入试运行”，不能把开发环境运行成功表述为生产可上线。
